# 设计文档 · 麦门开饭 McRogue

## 1. 一句话

把「今天吃什么」从**一次性的计算题**，变成**一局有三回合、有取舍、能晒结果**的游戏；
所有数值来自麦当劳 MCP 的真实数据。

---

## 2. 为什么是"游戏"而不是又一个点餐助手

（本节为项目立论，写给自己与评审看。）

市面上已有大量「输入预算 → 查菜单 → 领券 → 核价 → 下单」的线性工具。
它们解决"这一单怎么最省"，但有两个天然短板：

1. **与用户的真实动机错位**：人们点麦当劳时的真实纠结不是"求最优解"，而是"我今天想吃点什么、值不值"；
2. **不可传播**：一次点餐的结果没有分享价值，工具用一次就沉淀不下来。

McRogue 把痛点重新表述为**一日三餐的资源分配问题**：
预算有限、热量额度有限、券会过期、活动每天不同——这本身就是天然的**肉鸽约束**。

> **把"算一单"变成"打一天"**：结果是一张可以晒的战报，而不是一串价格。

## 3. 核心循环

```
开局定盘
  ├─ now-time-info            判定时段
  ├─ query-nearby-stores      选门店
  ├─ campaign-calendar        抽「今日事件」
  ├─ auto-bind-coupons        领券（道具入库）
  └─ 四路券池汇总              标出「临期券」
        │
        ▼
   ┌──────────── 三回合（早 / 正 / 晚）────────────┐
   │  query-meals  → 出「手牌」                     │
   │  query-meal-detail + list-nutrition-foods 补全 │
   │  玩家选 1~2 件                                 │
   │  calculate-price 真实核价（含券）              │
   │  score.py 结算：省钱率 / 热量达成 / 券利用     │
   └───────────────────────────────────────────────┘
        │
        ▼
     战报（总分 + 段位 + 锐评 + 可分享图）
        │
        └─ 用户显式确认后 → create-order（可选）
```

### 回合之间的张力（肉鸽感来源）

| 机制 | 作用 |
|---|---|
| 午餐超热量 | 晚餐额度被压缩，逼出取舍 |
| 用掉临期券 | 后续回合券池变小，"现在用还是留着"成为决策 |
| 今日事件 | 当月真实活动改变约束（加价购、联名限定、限时优惠） |
| 取餐方式 | 到店自取省配送费 vs 麦乐送省时间，影响预算分配 |

## 4. 双形态：为什么必须有一个"不用 Token 也能玩"的版本

| 形态 | 文件 | 面向谁 | 作用 |
|---|---|---|---|
| **Skill 本体** | `SKILL.md` + `scripts/` | 装了 WorkBuddy + MCP Token 的人 | 真实数据、真实核价、可真实下单 |
| **可玩网页版** | `docs/index.html`（单文件，构建产物） | 所有人 | 零门槛体验、可分享、可嵌入 |

**两者共用同一套结算逻辑**（`scripts/score.py` 的规则在网页版中以等价 JS 实现），
保证"网页版玩到的规则"和"Skill 里跑到的规则"一致。

设计上刻意让网页版**内置真实菜单快照**（`data/snapshot.json`），
使离线状态下的体验仍然是"真的麦当劳菜单"，而不是编造的数字。

### 附赠：两个即开即玩的小游戏

除主玩法外，仓库里还有两个**单文件、离线可玩**的小游戏，都用真实营养数据当数值引擎：

| 小游戏 | 文件 | 一句话 |
|---|---|---|
| 麦门幸存者 McSurvivor | `docs/neon.html` | 幸存者类：自动开火 + 走位 + 三选一构筑；敌人血量/速度由 kcal 派生 |
| 出餐口大作战 McChow | `docs/arcade.html` | 接住出料口倒下来的真实菜单，吃撑结束；12 张手绘风餐品立绘 |

两者都有确定性构建管线（`scripts/build_*.py`）与无头冒烟测试（`scripts/smoke_*.mjs`）；
出餐口大作战还有一条独立的素材管线（文生图 → 抠底归一化 → base64 内联，见 `scripts/prepare_sprites.py`）。

## 5. 战报（传播单元）

结算后产出一张竖版战报，包含：

- 三回合实际花费与省钱率
- 全天摄入热量 vs 额度
- 用掉的券
- 段位与一句话锐评
- 项目二维码/链接

网页版用 Canvas 直接导出 PNG，**长按保存即可发朋友圈**。

> 战报是本项目的"传播单元"：游戏可以只玩一次，但战报会被晒出去。

## 9. 联调实测发现（官方文档未载）

以下三条是实际跑通后记录的事实，官方 MCP 文档里没有写：

1. **服务端实为 35 个 Tool** —— 公开文档的表格只列了 33 个，实测多出
   `query-promotions`（团餐满减/满折规则）与 `query-survey-coupon`（订单满意度奖券）。
2. **`query-nearby-stores` 的隐藏约束** —— `searchType=2`（按位置）时，
   `city` 与 `keyword` **必须同时非空**，只传其一都返回 `600058 城市名或者关键词不能为空`。
3. **`query-meals` 的时段技巧** —— 传入 `reservationDate`（格式 `yyyy-MM-dd HH:mm`）
   会返回**该时刻**的菜单。不传只能拿到当前时段；本项目借此拿到**早餐菜单**，
   否则晚上跑的时候永远看不到麦满分系列。

另外实测：`list-nutrition-foods` 的营养表在 `structuredContent.data` 里（含真实换行），
而 `content` 文本块中是 JSON 转义过的 `\n`，解析时不能混用。

## 10. 边界与合规

- 不下单（默认）；下单必须显式确认；
- 不做医疗/营养建议，只呈现官方数值；
- 不与其他品牌作比较（活动规则明确禁止）；
- 不硬编码 Token，不落盘个人信息；
- 不使用任何自动化手段影响排名。

## 11. 真实感层与每日挑战（2026-10-09 深夜）

三个小游戏共用的「真实感」补强，全部来自官方 MCP、构建期内联、运行时零网络：

| 能力 | 数据来源 | 落地 |
|---|---|---|
| **真券图** | `available-coupons` → `couponImage`（此刻真实在售的券） | 出餐口大作战：掉落的券是真实券图 + 金边；战报新增「本局抢到的真券」区 |
| **活动海报开场** | `campaign-calendar` 的「今日」活动内嵌海报 | 出餐口大作战开始页：当天真实活动卡（海报 + 标题 + 摘要） |
| **每日挑战** | 本地日期（不需要网络） | 两个小游戏开局种子 = `YYYYMMDD` ⇒ 同一天全世界同一局；`?d=YYYYMMDD` 回玩历史；结算页印挑战编号 |

**为什么内联而不是外链**：券图 CDN 链接带签名（约两周过期），且单文件游戏承诺
「离线可玩 / 零依赖」——运行时拉外链会同时破坏这两条，弱网下还会再次引入白屏风险。
所以只在构建期做「拉一次 → 压缩 → 内联」：

- 素材管线：`scripts/fetch_realtime.py`（拉券 + 当日海报，落 `data/realtime.json`）→
  `scripts/prepare_realtime.py`（Pillow 压成小体积 webp：券 ≤14KB/张、海报 ≤60KB）→
  `build_arcade.py` base64 内联。产物 210KB → 293KB，仍在 350KB 弱网预算内。
- CORS：券图域名 `img.mcd.cn` 实测 `ACAO:*`，本就允许进 canvas；内联后连 CORS 判定都不需要。
- 去重与确定性：同局掉落的券由种子驱动 ⇒ 同一颗种子掉同一张券；战报按券去重。

测试口径（负向控制实测各有红）：`smoke_arcade.mjs` §13 / `smoke_neon.mjs` §12。

## 12. 套餐化出料 + 今日优惠（2026-10-11）

出餐口大作战的核心循环改成「按真实套餐出料」，并给结算页加一个「玩一局换当天优惠」的兑现点：

| 改动 | 数据来源 | 落地 |
|---|---|---|
| **套餐化出料** | 菜单里的真实套餐（`*三件套 / *套餐`，`data/snapshot.json`） | 出料口一次只倒**一份套餐里的一件**：先主食、再配餐，件与件间隔（套餐内 ×0.62、套餐间 ×1.5 基准间隔）；HUD 在出料口下印「套餐名 ②/③ · 省¥x」 |
| **集齐奖励** | 套餐价 vs 单点合计的**真实价差** | 一份套餐的件全吃到 ⇒ 额外加分 + 记「省 ¥x」进战报；漏掉任一件不算集齐 |
| **今日优惠** | `available-coupons` + 当日活动文案里抠出的「x 元（起）」 | 结算页与战报新增「今日优惠 · 打完这局解锁」：真券图 + 当日活动优惠价；没打完不给看 |

**套餐拆件是派生的，但可被价格证伪**：MCP 只给「巨无霸三件套 ¥51.5」这一条，不给组成明细。
派生规则 = 主食（套餐名去后缀，必须命中营养表）+ 常规配餐（早餐：脆薯饼+鲜萃咖啡；正餐：中薯条+中可乐），
再用「**套餐价 ≤ 单点合计**」做门——不过门的套餐直接剔除（宁可少几份也不编造组成）。
过门的 23 份里价差 0~3 元，正好是「这份套餐真实省下的钱」，顺手变成集齐奖励的数值。

**平衡随套餐重标**：一份套餐 ≈ 400~1150 kcal，胃容量上限 100（=1000kcal）会让一局只够吃一份套餐，
故改成 **240（= 2400 kcal，一天的量）**；段位线按贪吃机器人实测（中位 ~1000 分）重标为
3600/2200/1400/700。饱腹口径不变（kcal/10）。

测试口径：`smoke_arcade.mjs` §14（拆件可证伪 / 顺序与间隔 / 集齐与漏件 / 今日优惠解锁前收起）。
